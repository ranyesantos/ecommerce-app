platform · plano de evolução · etapa 1 de 6

Web app Laravel

A etapa 1 entrega uma aplicação web tradicional com o CRUD do catálogo. O Laravel é o ponto inicial e dono do catálogo; depois, pedidos, estoque e pagamentos entram como serviços Node comunicando-se por RabbitMQ.

  • banco por serviço
  • Laravel = web app + BFF + catálogo
  • regras nos próprios serviços
  • catálogo isolado por feature slice
  • dinheiro em centavos

Etapa 1

O que o web app entrega

  • CRUD de produtos: UUIDv7, SKU único, nome, preço em centavos, ativação e lixeira — com validação.
  • Esqueleto do monorepo: catalog-app/, packages/contracts, infra/docker.
  • Rotas web, formulários e views server-side para o CRUD do catálogo.
  • Docker Compose sobe catalog-app + catalog_db do zero.
  • Suite Pest cobrindo as regras do catálogo.
  • ADRs: web app/BFF, feature slice, database-per-service, centavos.

Sem pedidos nesta etapa. A primeira entrega é exclusivamente o CRUD web do catálogo; a entrada de pedidos será adicionada depois como uma ação web que publica um comando para o orders-service.

A seguir · etapa 2

RabbitMQ chega, serviços nascem um por um

2a

Broker no ar

infraestrutura
  • RabbitMQ no compose: exchange topic ecommerce.events, filas por consumer group, escada de retry 5s/30s/2m via TTL+DLX, DLQ, Management UI.
  • Nasce o packages/core-node: ack pós-commit, inbox de idempotência, classificação de erro recuperável × permanente.
2b

Serviço de Pedidos

Node · TypeScript
  • O Laravel recebe a ação web de criar pedido e publica order.placement.requested; o orders-service persiste e publica order.created.
  • Orders-service consome, persiste o pedido e conduz a máquina de estados da saga.
  • Nasce antes do estoque: é a cabeça do fluxo — sem ele, os demais consumidores não têm producer.
2c

Serviço de Estoque

Node · TypeScript
  • Consome order.created e reserva — estoque nunca negativo, UPDATE condicional atômico.
  • Publica stock.reserved ou stock.unavailable.
2d

Serviço de Pagamentos + fechamento

Node · TypeScript
  • Consome stock.reserved, autoriza e publica payment.authorized.
  • Tokens determinísticos: card-success · card-transient-failure · card-rejected.
  • Fechamento do ciclo: captura, confirmação da saída do estoque, pedido completed.

Arquitetura alvo da etapa 2

Eventos no centro, serviços ao redor

setas duplas = consomem e publicam eventos · routing keys por domínio

O navegador fala somente com o Laravel. A ação web de pedido publica o comando order.placement.requested; o orders-service publica order.created depois de persistir o pedido. Leituras síncronas internas podem existir quando justificadas, mas não fazem parte do caminho de alteração da Saga.

Fluxo do pedido

Seis passos, seis eventos

1 order.placement.requested — Laravel publica (itens + preços congelados)orders-service consome e persiste o pedido
2 stock.reserved — estoque consome order.created e reservaorders atualiza o estado do pedido
3 payment.authorized — payments consome stock.reserved e autorizaorders atualiza o estado do pedido
4 order.confirmed — orders publica a confirmaçãopayments escuta para capturar
5 payment.captured — payments captura o valor autorizadoorders e estoque escutam
6 stock.confirmed — estoque confirma a saída definitivaorders conclui o pedido

Compensações chegam na etapa 6, na mesma coreografia: stock.unavailable, payment.declined, order.cancelled com liberação de estoque e void da autorização.

Critérios de conclusão

Etapa 1 está pronta quando

  • CRUD web de produtos completo, com validação — SKU único, preço maior que zero.
  • Feature slice Catalog com controllers, requests, Actions, modelo e testes próximos.
  • docker compose up do zero sobe catalog-app + catalog_db respondendo.
  • Suite Pest verde, cobrindo as regras do catálogo.
  • ADRs registradas: web app/BFF, feature slice, database-per-service e centavos como inteiro.

Assim que esses critérios estiverem verdes, a etapa 2 começa colocando o RabbitMQ no ar e criando os serviços Node um por um.
