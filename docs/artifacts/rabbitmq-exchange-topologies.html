01 / concentrada

Uma exchange para negócio, retry e DLQ

funciona · mistura papéis

Todos os caminhos passam por ecommerce.events. Routing keys diferentes tentam manter as rotas legíveis, mas a exchange passa a carregar tanto o contrato de negócio quanto a mecânica de entrega.

  • ganhoUma única porta de entrada para declarar e observar.
  • riscoUm binding operacional mal configurado pode redistribuir uma mensagem de retry como se fosse evento novo.
  • custoPermissões e dashboards precisam entender duas linguagens no mesmo lugar.

02 / separada

Negócio no centro. Transporte nos bastidores.

✓ recomendação para a próxima ADR

ecommerce.events é o contrato público de negócio. Retry e DLQ ganham exchanges operacionais próprias: continuam no mesmo broker, mas não fingem ser eventos que um novo consumer deveria assinar.

  • ganhoBindings de negócio ficam pequenos, previsíveis e fáceis de expandir.
  • ganhoPermissões, métricas e alertas distinguem evento de falha.
  • notaUma exchange extra é infraestrutura interna — não um novo domínio nem um novo contrato.

03 / retorno implícito

Negócio no centro. Default exchange na volta.

enxuta · menos explícita

O evento normal continua em ecommerce.events. Na volta do retry, a fila TTL publica na exchange default "" usando o nome da fila principal como routing key.

  • ganhoO retorno cai diretamente na fila certa e não passa por outros bindings.
  • riscoA rota é implícita: quem lê o desenho precisa conhecer a regra especial da exchange default.
  • custoDocumentação e observabilidade precisam explicar uma exchange sem nome.

02 / peça de trabalho

O evento não é a topologia.

O publisher conhece uma exchange e uma routing key. O consumer conhece sua fila. O envelope carrega o contrato, não a infraestrutura.

mensagem de negócio / v1

catalog.product.created

Publicada após o produto ser persistido no catálogo. Preço é inteiro em centavos; o modelo Eloquent não atravessa o broker.

{
  "event_id": "01913d5c-7c2b-7a4b-9f0e-42f8a6b10001",
  "event_type": "catalog.product.created",
  "event_version": 1,
  "occurred_at": "2026-08-24T15:30:00Z",
  "correlation_id": "01913d5c-7c2b-7a4b-9f0e-42f8a6b10002",
  "payload": {
    "product_id": "01913d5c-7c2b-7a4b-9f0e-42f8a6b10003",
    "sku": "SKU-001",
    "name": "Caderno de estudo",
    "price_cents": 1990,
    "is_active": true
  }
}
  • event_idIdentidade única para deduplicação e inbox do consumer.
  • event_typeNome estável do fato de negócio, usado na routing key.
  • event_versionPermite evolução v1/v2 sem quebrar consumidores existentes.
  • occurred_atQuando o fato aconteceu no domínio — não quando o broker o entregou.
  • correlation_idFio de rastreio que atravessa logs e futuras etapas da plataforma.
  • payloadContrato explícito: só dados necessários para o próximo consumidor.

04 / o que existe agora

A etapa atual é pequena de propósito.

A infraestrutura pode ser declarada antes do consumer, mas só o caminho de publicação é exercitável neste momento.

● rodando

Broker

RabbitMQ no Docker Compose, com Management UI, exchange e topologia declarativa.

● em foco

Publisher Laravel

Após criar um produto, o Laravel monta o envelope e publica catalog.product.created.

○ próximo

Consumer

Sem uma fila vinculada e um consumer, retry, redelivery e DLQ não têm uma falha real para atravessar.

Limite importante: antes do Outbox existe uma janela entre commit no PostgreSQL e publicação no RabbitMQ. O ack tardio e a idempotência mitigam duplicações; a atomicidade completa chega na etapa 4.

06 / placa final

A topologia que cabe nesta etapa.

✓ recomendação de trabalho

ecommerce.events
para negócio.

ecommerce.retry e ecommerce.dead-letter ficam como circuitos operacionais explícitos, prontos para quando o primeiro consumer nascer. A escolha ainda precisa ser consolidada em ADR.

  1. 01Publicar agora: produto persistido → envelope v1 → exchange topic → routing key catalog.product.created.
  2. 02Declarar a estrutura: filas principais por consumer group, escada TTL+DLX de 5s/30s/2m e DLQ terminal.
  3. 03Exercitar depois: adicionar consumer mínimo para produzir ACK, falha recuperável, redelivery e DLQ observáveis.
  4. 04Registrar o limite: commit e publish não são atômicos nesta etapa; Outbox elimina essa janela nos serviços futuros.
